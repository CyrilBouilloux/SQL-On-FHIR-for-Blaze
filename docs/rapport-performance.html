1. Durée du run de la vue Observation

5 essais, 58 425 lignes, même empreinte de résultat à chaque essai.

Le premier appel est ~4× plus lent (chauffe de la JVM) ; ensuite le débit stabilise ≈ 140 000 lignes/s.

2. Latence de lecture : aucun effet des balayages concurrents

25 lectures GET /fhir/Patient/<id> à 1/s, toutes en code 200.

Rapport p95 avec / sans = 0,99. Seuil visé par F-009 : ≤ 2×.

3. Mémoire : le tas ne gonfle pas avec la taille de la vue

Pic du tas retenu (Mo) pendant le run, vue de 5 520 lignes vs 58 425 lignes (×10,6), 3 essais — T-043.

Ratios 58 425 / 5 520 : 0,991 ; 1,003 ; 0,995. Le tas est identique pour 10× plus de lignes — aucune rétention proportionnelle. Idem pour la variante « flux » (0,980–0,993).

Réserve. Le témoin rouge de l'instrument n'est pas rouge : une variante qui retient tout donne le même pic que celle qui streame (0 essai sur 3 au-dessus de 1,2×). L'instrument (pools mémoire JVM) ne discrimine pas à cette taille ; la garantie « mémoire constante » n'est donc pas encore démontrée. C'est l'objet de F-009 (grand jeu, statut proposé).

4. Autres relevés

  • Vue refusée (plafond 10 000 lignes) : réponse 422 en p50 8,3 ms, p95 17,3 ms.
  • Tas au repos : 297 Mo ; pic pendant un run : 326 Mo (+10 %).
  • Le banc générique bench/run.py (4 scénarios : ingestion en masse, écriture unitaire, recherche par compartiment et par token) existe, hérité de fhir-platform ; aucun relevé propre à Blaze n'y a été produit dans ce dépôt.
  • Non réalisé : mesure sur grand jeu et latence pendant un export asynchrone (F-009, non démarré).
